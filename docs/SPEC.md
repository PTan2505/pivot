| 7     | Screenshot                                | Captured automatically with Playwright when a URL is added (1440×900 viewport + full page). There is a button to capture again and a manual upload. **Updated 2026-10-28:** before the full-page capture, the app scrolls the whole page so content that only appears on scroll is also in the image: lazy images, items that appear when scrolled to, infinite-scroll lists, and pages that scroll inside an inner frame. The "Load more / Show more / Xem thêm" button (only `button` elements are clicked, at most 8 times, links are never clicked) **is clicked only when "Expand content" is on**, off by default (updated 2026-10-31, decision #12). Stops when the height no longer grows, or at the 12000px cap, or when the step/time limit runs out (60 steps, 45 seconds). The full-page image is cut at 12000px; if the full-page capture fails, the viewport image is still kept. **Updated 2026-10-31:** the page is scrolled with the mouse wheel like a viewer would, so scroll-reveal effects and content loaded on scroll are triggered. The full-page image is stitched from separate 1440×900 screens, captured one after another from top to bottom, and each screen waits for images to load and effects to finish (about 0.5 seconds) before it is captured. This replaces a single capture as tall as the whole page, which stretched sections that are `100vh` tall and captured parts that had not yet appeared. Fixed parts that could repeat on every screen appear only on the first screen. These include the wide bar at the top edge (header), and everything that floats at the bottom edge, wide or narrow: the cookie banner, the promo bar, Dribbble-style "Start a project" buttons, the chat button. Tall, narrow sidebars, like those on docs pages, are kept as they are (updated 2026-10-31). **A Source is captured as a viewport only.** **Updated 2026-10-29:** pages that block automated browsers (HTTP 401/403/429, or a bot-check page such as "Just a moment…") and error pages (other HTTP 4xx/5xx) are not saved as images: the capture is marked failed, with a reason; the app does not fake a user agent to get past this. Each capture has a 120-second cap; past that it stops and reports failure, so one hung page does not block the queue. Capturing again replaces the old image only after the new image is saved, and keeps the cover image the user chose while the capture is running. **Original and Latest** (updated 2026-10-31, #18): the first successful capture is kept as Original (roles `screenshot-original`, `screenshot-full-original`) when a later capture replaces it; `screenshot`/`screenshot-full` are always Latest; images in between are deleted; identical images (same sha256) are not stored twice. The detail page shows Original first. Replacing an image by upload also keeps Original. A recapture whose full page fails keeps the old full-page image and marks it **Partial**. When the resource already has a cover chosen by the user or captured by the extension (the part of the page being viewed), the server no longer saves a viewport image, since it would repeat that cover, and only adds the full-page image (a Source gets nothing added); recapturing also removes the server's old viewport image in this case (updated 2026-10-30). A failed capture keeps the resource and the old images, uses the Open Graph image as a temporary cover if there is no cover yet, and shows a toast with an Open button. The **Replace** button on the detail page (swap image, also used for a Source): uploads one image to replace both the viewport and full-page images and make it the cover, so the card shows this image. Tall images (taller than 1.5 times the width) also get a **scrolling preview** version (the whole page, 720px wide) for the card to use; old images get a preview created the first time they are viewed. |

## 3. Security (added NFR-06, NFR-07)

- The server binds to `127.0.0.1` only.
- Middleware blocks requests whose `Host` header is not localhost (against DNS rebinding) and write requests whose `Origin` differs from the host (against CSRF). A write request must come from the app's own page (`Origin` matches the host, or `Sec-Fetch-Site: same-origin`) or carry the API token; a request with neither header (curl, a script on the machine) must also carry the token (updated 2026-10-31, decision #62). **Updated 2026-11-04** (Orchestrator v2 P0d, the rules live in `packages/core/src/request-guard.ts`): `Origin: null` (sandboxed frame, file) or an unreadable `Origin` is never treated as the app's own page, so the write request gets 403 instead of a server error; another page (different site, or same site on a different port) and the sandboxed mockup frame cannot open an API page in a tab or frame (`Sec-Fetch-Mode: navigate` from `cross-site`/`same-site` → 403), except `GET /api/design/mockups/:id` and `GET /api/assets/:id`; `GET /api/settings/token` returns the token only to the app's own page (`Sec-Fetch-Site: same-origin`) and to non-browser callers (no `Sec-Fetch-*` header), and 403 in every other case. The **read requests with side effects** (added 2026-11-04) — `GET /api/favicon` (downloads and stores a site's icon), `/api/search/external` (may download and store a catalog), `/api/metadata` and `/api/visibility` (fetch the URL passed in), `/api/resources/:id/compare` and `/compare/image` (decode and compare large images), and `/api/settings/token` — are served only when the request carries the API token (extension, MCP), or comes from the app's own page (`Sec-Fetch-Site: same-origin`, and `Origin`/`Referer`, if present, must also be the same origin), or is not from a browser (no Fetch Metadata, no `Origin` or `Referer` from elsewhere). In every other case (an `<img>` tag or `fetch` from a page on another site or another port, the sandboxed mockup frame, `Origin: null`, contradictory metadata) the proxy returns 403 before the route runs, so the side effect does not happen. `same-site` is not treated as `same-origin`. Other read requests pass through as before (assets and mockups are needed by the extension and other pages; the response is unreadable because there is no CORS). A browser too old to send Fetch Metadata is treated like a non-browser caller: this is a remaining risk. **Trust boundary:** every process on this machine (same user) is trusted, because it can read the token file and set any header itself; Fetch Metadata, `Origin` and `Referer` are used only to block a browser being abused by another page, because a web page cannot forge those headers. The token check compares against the exact stored token (it does not just look for an `Authorization` header), runs in the proxy before every route, and **writes nothing**: when no token exists yet, every token is wrong, and a request carrying a made-up token does not create one (updated 2026-11-04). The app listens only on `127.0.0.1` (`npm start`, `npm run dev`, and now also `pnpm --filter web dev|start` with `-H 127.0.0.1`), so another machine on the network cannot send a request with a forged `Host`. On a machine shared by several accounts: another account on the same machine can still call `127.0.0.1` and read the token through the route; this is a pre-existing risk, not yet handled.
- Fetching metadata and screenshots: `http/https` only, resolve DNS and block private, loopback and link-local IPs (SSRF). IPv6 is checked byte by byte: forms that carry an IPv4 address (`::ffff:…`, `::…`, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`) follow the IPv4 rules; `fc00::/7`, `fe80::/10`, `fec0::/10`, `ff00::/8` are blocked (updated 2026-10-29).
- **Redirects when capturing** (added 2026-10-30): Playwright can only block the first request of a redirect chain, so before opening the browser the server follows the URL's redirects itself (checking each step) and then opens the final page directly. During capture, every redirect step of the page and of its sub-resources (images, scripts…) is checked. If the page or a frame tries to open a private address, or a redirect step leads to a private address, the capture is cancelled, no screenshot is stored, and the message "The page sent the browser to a private address" is shown. Service workers are blocked during capture. One small risk remains: a redirect that happens only in the browser (the server answers differently to a browser) may have sent a GET request to a private address before it was detected, but nothing from it is stored.
- Upload: 200MB per file limit, MIME checked against an allowlist.
- Writing files outside the data folder happens in only a few places, all started by the user: export bundle, share pack, backup (following the destination folder rule in §1 #13), and Save skill to disk (owner only, needs a passphrase).

## 4. Chrome extension (added 2026-10-26, moved from P2)

- Popup (⌥⇧S): captures the visible part of the tab (so a signed-in page is visible) and reads the title/description from the page DOM. When a shot opens as a modal (Dribbble, Behance), the address bar has changed to the shot but the canonical is still the page underneath: in that case it saves the shot's URL, takes the title that is currently displayed, and leaves the description for the server to read from the shot's URL (updated 2026-10-31). Saving a page takes two steps (updated 2026-10-30):
  1. **Pick a type**: a grid of the commonly used types (Reference, Source, UI Library, Image & Video, Animation, Font & Palette), the other types behind "More types". Nothing can be saved at this step.
  2. **Details**: the tab image in the same aspect ratio as the captured tab, uncropped (toggle "Attach this view"), the title, then only the facets that fit the type. Each facet is an input with a suggestion dropdown (autocomplete): clicking it shows the values already used, most used first; type to filter; ↑↓ and Enter to pick, or create a new value with the Create "…" row; a picked value shows as a chip with a remove button. Reference asks only for Page type, Domain, Style (not Pattern, because Pattern suits components better; it can still be added in the app). Description, plain tags, notes, collection and the option to let the server capture more are in "More details", closed by default.   - Saving a selected piece of text is still one form, as before.
- **Already-saved pages and PIVOT's own pages** (updated 2026-10-31): if the URL already has an item of the same type, the popup still warns "Already saved as …" and the Save button becomes **Save again**, so that creating a second copy is deliberate. A page of the PIVOT app itself (same origin as the extension's server URL) cannot be saved: the popup says "This is PIVOT itself", and quick save shows an error.
- Quick save (⌥⇧D), and a right-click menu for pages, links, images and selected text (saved as a snippet/prompt; the selected-text items show only while Other resource types is on, §1 #34). Quick save and link save do not create duplicates: if the URL already has a reference, the old item is reopened and "Already in PIVOT" is shown (`/api/clip` accepts `ifExists: "skip"`; by default it still creates a new item) (updated 2026-10-29).
- Pairing uses an API token (`~/.pivot/api-token`, viewed/changed in Settings). Write requests from another origin must have `Authorization: Bearer <token>`.
- **Token check** (updated 2026-10-30): opening the popup calls `POST /api/ping` immediately, so a wrong token shows the Connect screen before anything is typed. If the token is changed while the popup is open, Save reports an error right in the form with an "Open extension settings" button, and everything already entered is kept so Save can be pressed again.
- **Source through the extension** (updated 2026-10-30): the attached tab image is the Source's first screenshot, so the option to let PIVOT capture ("Take a screenshot in PIVOT") appears only when the tab image is not attached; the message after saving says exactly what the server will do. Quick save (⌥⇧D) on the home page of a known site saves it as a Source.
- **Offline queue (Pending Sync)** (added 2026-10-31, decisions #37, #43, #45, #46, #53): every save from the extension (popup, quick save, right-click menu) is first written to the extension's IndexedDB ("Saved locally"), with its image, and only then sent. The item leaves the queue only when PIVOT answers successfully ("Synced"); the message "Saved to PIVOT" appears only then. When PIVOT is off, the popup still allows saving (tags and collections come from the last cache), says "Saved locally" with the reason, and the extension icon shows the number of pending items.
  - Resending happens when the popup opens, when Chrome starts, and every minute (`chrome.alarms`, which runs only while the queue has items). A temporary error (5xx, 408, 409, 429) is retried with a wait that grows from 30 seconds to 30 minutes, and never gives up. When PIVOT is off or the token is wrong, the whole pass stops and the items stay as they are. Any other 4xx error moves the item to "needs attention": it is not resent automatically; the popup has Retry and Discard (Discard must be pressed twice). It never recaptures the page when resending. The popup warns when the extension's storage is more than 80% full.
  - **No duplicate saves:** each item has an id (`clientRequestId`); `/api/clip` records that id in the `clip_requests` table, so a resend after a lost response receives the item that was already created (`replayed: true`); when two sends arrive at the same time, the later one waits for the first (at most 10 seconds, after which it gets 409 and retries later).
  - **Capabilities:** `GET /api/capabilities` returns `{ apiVersion, features }`. The extension checks the features it needs (`clip.client-request-id`, `clip.expand-content`…) instead of comparing version numbers; if the server lacks a feature, the item stays in the queue with the reason "PIVOT needs an update" and is not sent with options missing. The popup tells apart PIVOT being off, a wrong token, and PIVOT being older than the extension.
  - The target of a notification (click to open) is stored in `chrome.storage.session`, so it can still be opened after the service worker has been stopped. A system notification does not contain page content when a save fails.
- **Searching external sources in the popup** (updated 2026-11-01, decision #42): there is only **Elsewhere**, which opens the sources' search links (link-out, §18). The popup has no Direct Search and will not get one, even when the web app has Hybrid Search.
- Endpoints: `POST /api/clip`, `GET /api/lookup`, `POST /api/ping`, `GET /api/capabilities`, `GET|POST /api/settings/token`.

## 8. Finding and reusing (added 2026-10-30)

- **Sort**: Recently edited (default), Newest first and Oldest first (by date added), Title A–Z. URL parameter `sort=updated|created|oldest|title`; `GET /api/resources` accepts the same values. When there is a search keyword, items matching the title still come first, then the chosen order.
- **Combining filters**: search (`q`), tags and facets (AND), type or section, and source (`via`) all apply at once.
- **How a search query is read** (updated 2026-10-31, `packages/core/src/query.ts`, shared by the library and MCP):
  - Each word must match at the **start of a word** (not in the middle of a word, so "sign" no longer hits "design") in one of these places: title, description, notes, content, URL, tag/facet name, or the **category name of a Source** (for example "Type & Color", "Inspiration").
  - Matching is prefix-based, and a plural finds the singular ("icons" finds "icon").
  - Words with no meaning are dropped (a, the, in, of, for, to…).
  - Generic words (page, site, screen, example, ui, ux, design, product…) are not required to match, unless the query consists only of such words.
  - Some groups of synonyms in the facet vocabulary count as one: login ↔ sign in ↔ auth, docs ↔ documentation, pricing ↔ plans, palette ↔ colors, e-commerce ↔ shop, animation ↔ motion, mobile ↔ iOS ↔ Android, inspiration ↔ gallery ↔ showcase.
- **Order when there is a query**:
  1. the whole query is in the title;
  2. every word is in the title;
  3. a tag or category matches;
  4. the description matches;
  5. the remaining fields.

  Within the same tier the chosen sort applies, and finally the id, so the same query always gives the same order.

- **Search evaluation set**: `packages/core/test/search-eval.test.ts` runs 33 real queries on a copy of the titles, descriptions, URLs and facets of 25 real references and 45 real sources (`test/fixtures/`). The test fails if Recall@5, Precision@5 or MRR drops below the recorded level. On 2026-10-31: 0.773 / 0.702 / 0.848 with substring matching, and 0.956 / 0.826 / 0.977 after switching to the new query reading.
- **Paginated search for agents and MCP**: `GET /api/resources?paged=1` uses `searchResources()` (`packages/core/src/search.ts`).
  - Parameters: `q` (at most 200 characters), `types` or `section`, `facet=kind:name` (repeatable, AND, case-insensitive), `collection`, `via`, `sort` (`relevance`, `updated`, `created`, `oldest`, `title`), `limit` (1–50, default 20), `cursor`.
  - Result `{ results, total, nextCursor, sort, unknownFacets? }`. Each result has id, type, title, host, `sourceUrl` (http/https only), description (at most 280 characters), at most 8 facets, `hasScreenshot`, created and edited dates. It has no storage path, no asset id, no notes and no content.
  - A cursor is tied to the exact query that produced it: using it for a different query gives 400 `invalid_cursor`.
  - A facet that is not in the library returns an empty result with `unknownFacets`.
  - Items in the Trash are never returned.
  - Without `paged=1`, the route returns an array as before, for the UI.
- **Clearing filters**: when a search, tags or a source filter is active, the toolbar has a **Clear filters** button that clears all three (the search field on the top bar is cleared too). Type, section and source category are the page being viewed, not filters, so they are kept.
- **No results**: shows "Nothing matches “…”" with a Clear filters button. The page of a type that has no items yet shows "Nothing in <page name> yet".
- **Opening the original page**: the Open button (detail page) and the Open source button (card) open only `http`/`https` links. A URL with only a domain (like `attio.com`) gets `https://` added, so the link never becomes a relative path inside the app; a `javascript:`-style link shows no button.
- **Viewing the screenshot at full size**: on the detail page, clicking the image or the View at full size button opens the image in a frame as tall as the screen and as wide as the captured size (at most 1440px), scrollable from the top to the bottom of the page; there is a button to open the original file.
- **Detail page for types with images** (added 2026-11-02): reference, UI library, media, icon, animation, typography, source.
  - The image is on the left. On the right are groups ordered by how often they are used:
    - **Classification**;
    - **Notes & collections**;
    - **Source**: URL, "Captured from"; the description is cut to 3 lines, with a "Show all and edit" button that opens the edit field; **+ Published by** and **+ Original source** open their input only when clicked, and a field that already has data is always shown; the type's own fields; Links.
    - finally a secondary row: Type, date added, date edited, file count.

    Every old field is still there and still saves itself as before.

  - Below the image, the thumbnails and the **Annotate**, **Replace**, **Retake** buttons are in one row. The file name, size, file note and the Set as cover, Open original, Download, Remove buttons are in the "File details" section (closed by default), next to "Capture history". The collapsed gallery of text types keeps the old label ("Replace screenshot").
  - On a phone (below 640px), the Open, Copy, Context, Export, Trash buttons become a row right under the title; Open, Copy and Context are icon-only but still have a name for screen readers.
  - Types without images (skill, prompt, snippet, rule, checklist, MCP) keep the single-block info column as before.

## 10. MCP server for Claude Code (added 2026-10-31)

- **How it runs:**
  - `apps/mcp` is a **stdio** server: Claude Code starts it by itself.
  - The server reads data through the HTTP API of the running PIVOT app (`PIVOT_URL`, default `http://127.0.0.1:4321`), with an API token (`PIVOT_TOKEN`, or taken from `~/.pivot/api-token`).
  - So the database, storage and access rules stay only in the app; the MCP server does not read the database directly.
- **Build and registration:** build with `pnpm mcp:build`, then register with `claude mcp add pivot -- node <repo>/apps/mcp/dist/server.js` (detailed instructions: `apps/mcp/README.md`).
- **Tools:** defined in `packages/mcp-tools`, written against the `PivotSource` interface, independent of how the connection is made. An online server can reuse them later without rewriting. For now there are read tools only:
  - `search_references`: uses `searchResources` (§8). Can filter by facet (name), collection (name or id), source (host or id), types or section. At most 25 results per page, with a cursor. While Other resource types is off, a hidden section or type is refused with an explanation (updated 2026-11-18, §1 #34).
  - `get_reference`: link (http/https only), description, notes (at most 2000 characters), content (at most 8000 characters), facets, collections, and a list of images with their sizes. An item in the Trash is treated as nonexistent.
    - **Motion evidence** (added 2026-11-04, Orchestrator v2 P1a): a `motionEvidence` block, **derived at read time** from the assets the capture step already stored, with no new table, no migration and no write tool. `classification` is `observed` only when PIVOT recorded the page while scrolling (a `motion-video` and/or `motion-keyframe` asset), together with `scope: "scroll"`, `source` (how it was recorded, capture date, viewport, final URL), `recording` (the video asset, duration), `keyframes` (in scroll order, with `scrollY`), `states` (images of interaction states, `meta.state`) and `limitations` (scroll only, no hover/click/focus; no timing or easing measurement; what lies between two keyframes is inferred; the video cannot be viewed through MCP). With no recording it is `unknown`. The system never assigns `inferred` itself: that is a label the agent writes in the brief. Invalid numbers in meta are dropped (null), not guessed: dates must be valid ISO, durations and viewports must be positive, `scrollY` must not be negative, and a `meta` that is not an object is treated as empty. The keyframe and state lists have at most 12 items, with the total count. An old reference with no recording reads as `unknown`; its other fields do not change.

  - `get_reference_images`:
    - the cover image, scaled down so its longest side is at most 1568px;
    - a full-page screenshot scaled to 960px wide and then cut into slices at most 1568px tall, about 2000 tokens per slice;
    - at most 4 images per call; see the following slices with `fromSlice`;
    - `which: "keyframes"` (added 2026-11-04): the keyframes of the recording in scroll order, each image labelled "observed, PIVOT scroll recording" with its scroll position, plus the limitations; `which: "states"`: images of interaction states, labelled clearly as still images. Both page with `fromSlice` and take only assets of that reference itself. `structuredContent` carries every image label (`images`), the next page (`next`) and `limitations`, because some clients (Claude Code) show only this part and drop the text part. With no keyframes it returns `no_images`: it says the evidence is `unknown` when there is no recording, or that a recording exists but there is nothing to look at when only the video is left.

The user's words decide if they speak about motion; reconsider once after the user picks references;

    7. build **2–3 mockups** that really differ in structure (updated 2026-11-03: go to 4–5 only when the work needs wide exploration, or exactly the number the user asks for) using the target project's design system. For a **component** (updated 2026-11-03): each mockup puts the component in the page or container where it belongs and draws the states it has (hover, focus, disabled, loading, empty, error, long text) statically side by side; a small component often has only 2–3 truly different directions, so make 2–3 and say so, without padding up to 5; the brief gets an extra **Component API** line (props, variants, states, whether it extends an existing component or is new). The mockups are saved into the design session with `save_design_mockups` and the user gets the link to the session page in PIVOT (updated 2026-11-03, see §15). After that the agent runs the script `scripts/wait-for-decision.mjs` in the skill folder in the background: the script only reads PIVOT and exits when the session leaves `exploring`, and its exit wakes the agent. (updated 2026-11-16) The watcher belongs to the session that is talking to the user: when another agent (background, fork, subagent) builds or saves the mockups, that agent's watcher ends with it and cannot wake the main session, so the main session runs the watcher itself before it reports that the mockups are ready; likewise when it resumes or reports on a session that is still `exploring` and already has mockups. It never ends a turn that asks for approval without a watcher running. When PIVOT cannot store (`read_only`, the app is not running…), the agent uses the local **viewer** (`viewer/make-viewer.mjs` produces `index.html`: desktop, tablet, phone, keys 1–9, Replay, and a "Choose this version" button that copies a ready-made reply for the chat). From 2026-11-03 the viewer embeds each version into the page and runs it in a sandboxed frame with an empty origin and a strict policy: no network, no reading files outside the mockup folder (including through `..` or symlinks), no page navigation, no popups, no forms, no storage; navigation links are removed (`#anchor` is kept), and a version that navigates by itself is stopped. The policy is placed right after the doctype (or at the start of the file) so it applies to everything after it. Each version has a content **digest** (sha256, 12 characters), shown in the viewer and included in the copied "Choose this version" sentence. The viewer and PIVOT's mockup route turn DNS prefetch off (`x-dns-prefetch-control: off`, best effort only, not verified). CSS, images and fonts inside the folder are embedded; anything remote or outside the folder is removed and listed. Scripts run only in the version recorded under `--interactive` (motion prototype) and are removed otherwise;
    8. **approval** (updated 2026-11-10, see §1 #25): only the owner approves, with the **Approve this version** button on the session page, with a note and the owner passphrase. If the user chooses in the chat ("tôi chọn bản 3"), the agent only gives the session page link and waits, and does not write an approval itself. With no PIVOT (read-only, cannot connect), a clear agreement in the chat is the approval for that build, and the session status in PIVOT stays unchanged. Approval in PIVOT is the user's explicit approval: it is not recorded again by the agent, who follows the note (unless the note asks for a material change, in which case it asks again) and builds right away, so the user does not need to come back to the chat;
    9. code; motion uses the technology the brief chose (updated 2026-11-15): first of all what the project already uses; standard motion uses CSS (Web Animations API when a script must drive it), with no added library; advanced motion uses **GSAP** (ScrollTrigger, timelines, plugins; plus `@gsap/react` for React/Next.js), unless the project already has another motion library or every essential item can be done with CSS. A library may be installed at the build step only when the approved brief names it on the Technology line; interactive mockups use a GSAP file copied into the scratch folder and do not install anything into the project before approval. The agent reads the `gsap-*` skills as API documentation while building (`gsap-core`, the skill for the stack and the skill for the feature) and `gsap-performance` during QA.

    **Motion QA** (added 2026-11-04, Orchestrator v2 P1c, `motion.md` §9): each item in the brief's Motion block carries a number **M1, M2…**, kept the same throughout the session, so QA results trace back to the approved brief. The agent reads the approved brief (`get_design_session`) and saves the markdown and a JSON **plan** in the scratchpad (never in the target project): each item records the trigger (`load`, `scroll`, `hover`, `click`, `focus`, or `other` when it cannot be triggered by itself), the element that moves, what the brief expects (whether there is movement, which properties, the end state; duration and easing only when the brief states them) and the reduced motion behavior; budgets (`cls`, `longFrames`) come only from the brief's Performance line, with no tolerance of the agent's own. The skill's script `scripts/motion-qa.mjs` runs the plan in PIVOT's Chromium (it finds Playwright from the PIVOT repo through `packages/core`): real actions (page load, wheel, mouse, Tab) at desktop 1440 and phone 390, with full motion and with **browser-emulated** reduced motion, each mode twice (the second is a Replay from a fresh page; for a mockup in the viewer it uses the viewer's own Replay button). The preview must be local (a loopback URL, a file, or a mockup folder through the viewer with its sandbox and policy), never the PIVOT app itself (`PIVOT_URL`, default port 4321). The QA browser can reach only the preview's own origin (including its WebSocket, such as the dev server's reload channel): not another port or another name of this machine, not another host; every connection, including redirects, WebSockets and workers, goes through a local gate run by the script. WebRTC is turned off in two layers (updated 2026-11-09): a Chromium switch that allows UDP only through the gate (the gate carries no UDP) and an init script that removes the WebRTC constructors before the page's scripts. How effective each layer is depends on the binary, so the report records the binary that ran (headless shell or full Chromium) and its version. Measured on Chromium 156: the headless shell (the binary motion QA uses by default) accepts only `--force-webrtc-ip-handling-policy`, full Chromium accepts only `--webrtc-ip-handling-policy`, so the script passes both; the init script covers every frame tried in the headless shell but cannot enter a `sandbox` + `srcdoc` frame in full Chromium (the viewer's mockup frame is of this kind), so only the switch layer remains there. The regression test runs on each installed binary (it is skipped explicitly when full Chromium is absent): each vector (page, `srcdoc` sandbox frame, `src` sandbox frame, nested sandbox frame, constructor taken from a same-origin frame) must be able to send a packet when no layer blocks it, then 0 packets reach STUN at another address of the machine with each layer alone and with both, and `runPlan` must use exactly those launch options and that init script. This is evidence for the builds measured, not a guarantee for every browser or environment. The QA browser is set not to resolve any domain name by itself (`--host-resolver-rules`), and only the gate resolves what it lets through; that the browser makes no DNS lookups at all has not been measured on the DNS server side. `--allow-origin` adds another local origin the preview needs, `--allow-remote` adds a public host (a name that resolves to an address of this machine or of the internal network is still blocked); requests that can change data (every method except GET, HEAD, OPTIONS) are blocked and listed unless `--allow-writes` is given. Before using any of these three flags, the agent must stop and ask the user in the chat (which flag, what it opens, why), use it only after they clearly agree, and record that in the QA summary; without agreement it runs without the flag and reports what remains Not Verified. A flag only switches a script behavior: typing a flag is not permission, the script does not know whether the user agreed, and permission is the user's answer. A field in the plan cannot turn on any flag. The plan contains only selectors and expectations, with no shell commands or page scripts. Before a trigger the script waits for the page to settle; hover or click happens only when nothing covers the element. The result for each item is **Pass**, **Fail** or **Not Verified**: Pass only when every check ran and observed exactly what the brief says at every viewport, in both Replay and reduced motion; reading source, screenshots or guessing never becomes a Pass; a missing or covered element, a trigger that cannot be activated or a scroll that does not reach, a page that does not settle, an animation that finished before observation or is not finished at timeout, an element that disappears, a Replay that does not run, a brief that states no reduced motion behavior, or motion that declares no timing to compare is Not Verified. Reduced motion that turns off all movement is not automatically correct: the content must still reach its end state. The **overall** status is Pass only when every `essential` item of the brief has passed and every item of the brief has a check; a failing `detail` item is listed but does not decide. The script writes `report.md`, `report.json`, screenshots (and video with `--video`) with sha256, the browser, the preview identity (file sha256, viewer digest, the project's git revision) and the sha256 of the brief; each run writes into a new, empty folder with a run id, and `--verify report.json` re-checks the evidence (missing, altered, or foreign files from another run); that proves the files match the report, not that the report is genuine; exit codes: 0 Pass, 1 Fail, 2 Not Verified, 3 could not run (Playwright or Chromium missing: every item Not Verified, with no screenshot as a substitute). What the script does not check (timing feel, keyboard order, fallback, fidelity to the preview, cleanup when leaving the view, accessibility) the agent checks by hand and states clearly. `trace-check.mjs` counts motion QA runs separately from the specialist.

A specialist that is unavailable (not installed, or the Skill tool refuses) is skipped and recorded as `unavailable`, with nothing in its place.
    - Each specialist runs at most once per stage. The brief stores one ledger line per specialist: name, stage, run label, conclusion (`adopted`, `partially adopted`, `rejected`, `not applicable`) and reason. When a session continues, a specialist already in the ledger does not run again.
    - Conflicts between specialists: the specialist responsible for that area wins (UX → `ui-ux-pro-max`, visuals of a public page → Taste, motion → the motion specialist); accessibility and reduced motion always win over aesthetic suggestions. A suggestion that contradicts an approved decision is rejected or given to the user as a proposed change, never applied quietly.
  - **Choosing specialists** (updated 2026-11-12: from "optional" to a mandatory default by risk level). Use only skills verified as installed (read `SKILL.md` directly; do not trust an empty Glob result because skills are often installed through symlinks). Do not install, update or download anything. Do not add a specialist just because it is installed. Mandatory defaults:
    - quick fix: none, unless the user asks;
    - Small level: one specialist at the design stage, the one responsible for the problem (`ui-ux-pro-max` for UX or app screens, Taste for the look of a public page); a second only when it solves a separate problem the first cannot, and the reason must be stated;
    - new design (`pivot-design`) and Large level: always run `ui-ux-pro-max` on the brief; add Taste if it is a public web page; add `animate` when motion is at the standard or advanced level;
    - at the QA step there is always an AI slop check (`impeccable detect` if installed, the checklist, a critique for new designs and Large level). New designs and Large level also get an **`impeccable` audit through `pivot-specialist`** (reading the changed files, the after images and the detector result). Another audit may be added (Taste `lint.mjs`/`inspect.mjs` for a public page). QA audits do not count toward the design stage default;
    - a mandatory specialist that cannot run (not installed, the Skill tool refuses, or the session has no `pivot-specialist`) is recorded as `unavailable` (or `consulted` if only files were read), does not block the work, and has nothing in its place.

    Taste is for public pages. For dashboards, admin pages or app screens, use it only when the user asks clearly: the skill explains the rules that tend to conflict, waits for confirmation, then applies only the fitting parts. It never substitutes another Taste variant.

  - **Safe commands:**
    - `ui-ux-pro-max`: read-only search.
    - Taste: `lint.mjs`; `draw.mjs` writes to `<scratchpad>/taste` (direction history through `TASTE_SKILL_HISTORY`); `inspect.mjs` writes to `<scratchpad>/taste/inspect`, which makes `direction.json` readable. The scratchpad is outside the project.
    - `impeccable detect`: run only the binary of the exact version in `scripts/VERSION`, that is the bundled binary or a cached binary of the right version, checked with `engine-probe` and called directly. A missing or mismatched binary needs permission before downloading.
  - **Network, recorded separately for each kind:**
    - **Telemetry:** turned off with `DO_NOT_TRACK=1` and `IMPECCABLE_NO_TELEMETRY=1`.
    - **Version check:** there is an `IMPECCABLE_NO_UPDATE_CHECK` variable, but its effect has not been verified.
    - **Requests sent by the inspected page itself** (fonts, scripts, images…): no variable can block them, so ask first if the task does not allow loading remote resources.
    - **Downloading external assets** (`assets.mjs`, `picsum.photos` images): only when allowed.

    No environment variable turns off all network traffic.

  - **Forbidden unless permitted:** `--persist`, `polish`, `init`, `document`, `hooks`, and saving critique reports.
  - **Recording:**
    - a specialist that significantly affects the design direction is recorded in the brief and in the `details` of the decision, in the same design session (accepted, changed or dropped);
    - at Small level, the user's permission words are kept verbatim;
    - a quick fix that uses a specialist opens no session and is only mentioned in the summary;
    - a `deviation` is recorded only when the build is a departure from an approved requirement or detail (the four kinds of difference in `pivot-design`); a pre-existing defect or one outside the scope is reported separately and a later fix is proposed.

    Nothing is written into the target project.
- **Write tools** (added 2026-11-01, see §15): `save_design_brief`, `record_design_decision` (from 2026-11-10 it records only `change` and `deviation`, not approvals), `save_design_mockups` (added 2026-11-03: 1–9 versions per call, each version is `{ title, path }` or `{ title, html }`, with `interactive` added from 2026-11-10, see §1 #24; it inlines local CSS, images and fonts on the agent's machine, takes only files inside the mockup's folder (updated 2026-11-09, see the Mockups in the session section), drops scripts and files from other hosts and lists them again; only when the session is Exploring; each call is a new round, and sending the exact same set again returns the old round; it returns the session page link), `record_design_qa` (added 2026-11-12, see the QA record section), `record_chat_approval` (added 2026-11-15, see §1 #25), `set_design_status` (added 2026-11-02: sets `building` only when the session is Approved, sets `done` only when it is Building and, from 2026-11-12, when a QA record exists after the current approval; calling it again with the same status changes nothing; it never sets exploring, approved or abandoned), `get_design_session`, `propose_references` and `select_references` (added 2026-11-10, see §19), `suggest_metadata`, `annotate_reference`, `save_reference`. They need an API token (`PIVOT_TOKEN` or `<data folder>/api-token`); a read-only connection reports `read_only` and saves nothing, a wrong token gives `unauthorized`. **An online server** for other people to use: not built yet.

## 12. Capture reliability (added 2026-10-31)

Following Part B of [PIVOT_DECISIONS.md](PIVOT_DECISIONS.md), decisions #11, #12, #16, #17, #18, #26, #47, #55, #57.

- **Capture attempt:** each time the server captures, it writes one row in the `capture_attempts` table, with a status (`queued`, `capturing`, `completed`, `partial`, `failed`, `cancelled`), quality, error, and the times of request, start and end, plus context: the options used, colour scheme, viewport, final URL after redirects, and retry count. The detail page has a "Capture history" section (collapsed by default). `GET /api/resources/[id]/capture` returns the history; `GET /api/captures?status=` returns the recent attempts of the whole library.
- **Resource status** (`capture_status`): `pending`, `done`, `partial` (the above-the-fold screenshot exists, the full page failed), `failed`, `cancelled`. The queue survives a restart: `queued`/`capturing` attempts are run again.
- **Quality** (`capture_quality`), separate from status: `looks_good`, `needs_review`, `unavailable`. It is marked `needs_review` when the above-the-fold screenshot is almost blank, the page has a sign-in form (password field, little text), many images failed to load, fonts had not finished loading, or the full page repeats the same screen (the page cannot scroll). A suspicious screenshot **does not replace** a good Latest screenshot: the attempt is still recorded, the resource keeps the old screenshot and shows the note "The new capture looked wrong (…), so the previous screenshot was kept." Detection can be wrong; it does not block saving.
- **Bounded automatic retry:** at most 2 retries for timeouts, network errors and HTTP 502/503/504 (wait 5 seconds, then 20 seconds). HTTP 429 waits for `Retry-After` if it is no more than 10 minutes (60 seconds when there is no header), otherwise it reports an error. There is no automatic retry for 401/403, bot-check pages, unsafe URLs or other HTTP errors. While waiting, the resource stays `pending`; the Retry button still works and replaces that wait.
- **Cancel:** the Cancel button during a capture (`DELETE /api/resources/[id]/capture`) stops an attempt that is queued, waiting to retry or running (it closes the browser for that attempt). Screenshots saved earlier are kept; the resource goes back to `done` if it still has a screenshot, otherwise to `cancelled`.
- **Capture settings** (`app_settings` table, key `capture`; `GET|PATCH /api/settings/capture`, Capture section in Settings): `theme` = `dark` (default), `light` or `both`; `expandContent` = off (default). Each capture can override them: the menu next to the Retake button ("Expand content", "Light theme", "Dark theme", "Both themes"), the "Expand content" field in the extension popup, the `expandContent` field of `/api/clip`, and the `{ expandContent?, theme? }` body of `POST /api/resources/[id]/capture`.
- **Theme:** the server asks the page for the chosen colour scheme (`prefers-color-scheme`); it does not fake a theme with a filter. `both` also captures a light version as role `screenshot-variant` / `screenshot-full-variant`; if the two are byte-identical, the extra one is not saved. Each screenshot stores `assets.meta` (colorScheme, viewport, capturedAt, finalUrl, method), and the image label on the detail page states the scheme ("Screenshot · dark").
- Export and MCP use the Latest screenshot; the Original, the extra theme version, tablet/mobile screenshots and the motion recording stay in PIVOT (MCP still lists them in `get_reference`).
- **Extra captures on request** (added 2026-11-01, decisions #20, #21, #23, #47): the Retake menu has "Tablet and mobile too" and "Record motion (video and keyframes)"; the API accepts `viewports: ["tablet", "mobile"]` and `motion: true`. Never turned on automatically.
  - **Tablet** (820×1180) and **mobile** (390×844) are rendered by the browser at that size, with mobile mode, touch and a phone user agent, not a shrunken desktop screenshot. Each size has an above-the-fold and a full-page screenshot (roles `screenshot-responsive`, `screenshot-full-responsive`, `meta.viewportName`), kept in the same reference; a later capture replaces that size.
  - **Motion** (updated 2026-11-01): a video that scrolls the page from top to bottom like a screen recording (`motion-video`, webm VP9 1440×900, 30 fps): it holds for 1 second on the first screen, glides down at a steady 900 px/second (accelerating and decelerating over 0.6 seconds), and holds for 1 second at the bottom. Each frame is a screenshot taken at exactly its scroll position and then stitched together with the ffmpeg that ships with Playwright (`PIVOT_FFMPEG` to change it), so a slow page or one waiting for images does not make the video stutter; animations that appear on scroll still run. The mouse pointer is not placed on the page, so the video has no hover states or tooltips that pop up as it scrolls past. It scrolls to the bottom of the page (a page that grows as it scrolls keeps going), stops at the 12000px cap like the full-page screenshot, or after 75 seconds of capture. The video meta includes `durationMs`. Up to 8 keyframes (`motion-keyframe`, with the scroll position), taken evenly from those same frames. Complex interactions are not replayed. The server's browser has none of Chrome's sign-in state.
  - When the page has 2 or more running animations, videos or canvases, the capture records `motionLikely` and the detail page suggests "Record motion".
  - The extra captures run inside the same capture, before the resource stops being `pending`; any part that fails is recorded in the attempt's `context.extras` and does not break the main screenshot.
- **Capture later** (#56): "Capture later…" in the Retake menu (API `defer: true`) only creates a **request** (an attempt with status `deferred`), with no screenshot yet. A request does not run by itself, even when the server restarts; the Capture queue page has "Capture now" and "Drop" (`POST /api/captures/[id]/run`, `DELETE /api/captures/[id]`). The request time (`requestedAt`) and the capture time (`assets.meta.capturedAt`) are stored separately.
- **Compare and Design Version** (#28, #58): when an Original exists, the detail page has "Compare Original and Latest": the share of changed pixels, the Latest screenshot dimmed with changed regions tinted orange, and the time and colour scheme of each screenshot (`GET /api/resources/[id]/compare`, `/compare/image`). Dates, carousels and ads also count as changes, so the number is only a hint. At 25% or more it suggests "This looks like a redesign". **Save Latest as a new design version** (`POST /api/resources/[id]/versions`) creates a new reference, with the month in its title, sharing the Latest screenshot, with a `newer_version_of` link to the old one; the old one is kept as is, including its Original. There is no background website monitoring and no automatic version creation.
- **Capture health** (#59): the Capture queue page has a "Worth a look" section when a website has failed 3 or more times in 7 days without succeeding since, or when a reference's latest capture looks worse than the one before (`GET /api/captures/health`). No notification is sent for each failure.

## 14. Sections, links and private pages (added 2026-11-01)

Following Part B of [PIVOT_DECISIONS.md](PIVOT_DECISIONS.md), decisions #4, #8, #9, #22, #24, #25, #27, #34, #44, #48, #52.

- **A section is its own reference:** a part of a page (Hero, Pricing, Navbar…) is saved as a reference with `meta.section` = the section type, its position on the page (`rect` in CSS pixels from the top of the page), viewport, scroll position, selector (only a hint for finding it again, not relied on), page title and the way it was chosen (`select`, `crop`, `list`). No DOM or CSS is stored. The default name is `[Section] — [Source]` (the known page name or the host). A section always goes to the Inbox and does not ask the server to capture.
  - **Three ways to choose**, with no need to pick one first: **Select a section** (hover to highlight an element; ↑ selects the parent element, ↓ selects the child element, Enter saves, Esc cancels), **Crop** (drag a box), and **Pick from a list** (a list of landmarks and headed sections right in the popup, fully usable by keyboard). The right-click menu also has "Save a section of this page…".
  - **Capture:** the extension captures the open tab itself (so the signed-in state is visible), scrolls to the section and crops by `devicePixelRatio`. A section taller than the window is captured one screen at a time and then stitched, up to 6 screens (`truncated` when cut off). Afterwards the page is scrolled back to where it was. Chrome only allows capturing a tab twice per second, so the extension waits and retries. A page's fixed bars may repeat in the stitched image.
  - The section-picking script is injected only when you click (`activeTab` + `scripting` permissions); the extension does not watch pages and asks for no additional permissions.
- **Links** (`resource_links` table; `GET|POST /api/resources/[id]/links`, `PATCH|DELETE /api/links/[id]`): `same_source_page`, `part_of`, `related_to`, `variant_of`, `newer_version_of`. When a page is saved (a section included), PIVOT automatically links it with items that have the **exact same URL**: a section becomes `part_of` the page, anything else becomes `same_source_page`. The same website alone creates no link. A section can be saved before its page. Other links are added by hand on the detail page ("Links" section); a suggested link (`confirmed` = false, for example from an agent) has an accept button. Theme, viewport and Original/Latest are not links but screenshots of the same reference.
- **Private pages** (`GET /api/visibility?url=`): the server opens the URL **without cookies** and treats it as private if it gets 401/403, is redirected to a sign-in page (a path like `/login`, `/signin` or a host like `accounts.google.com`), or sees a password form. The extension adds signals from the tab: a visible password field, and app-style addresses (`app.`, `/dashboard`, `/settings`, `/account`…). This is only a guess and can be wrong in both directions.
  - **Popup:** a flagged page shows "This page looks private" with the reason, and the screenshot masker. Suggested regions (fields that already hold a value, emails, amounts) are on by default and can be turned off; draw more boxes with the mouse, or "Add a box" and move it with the arrow keys (Shift + arrow resizes, Delete removes). The Save button stays locked until you tick "I checked it: upload this screenshot with these masks", or untick "Attach this view".
  - **Quick save, the right-click menu and sections on a private page** are not sent: the item stays in the queue with status `needs_approval` (notification "Needs your approval") until you open the popup → **Review**, then choose "Upload with these masks", "Upload without the screenshot" or "Discard". "Sync now" does not send this item either.
  - **Masking** paints black over the pixels (`OffscreenCanvas`) on your machine before upload; the unmasked version never leaves the machine and is not stored on the server. A private page is not captured further by the server, because the server is not signed in. Cookies, sessions or passwords are never passed to the server. Chrome's permission does not replace your approval.

## 15. Design session and agent suggestions (added 2026-11-01)

Following Part A and decisions #1–3, #13, #19, #30, #34, #35 of [PIVOT_DECISIONS.md](PIVOT_DECISIONS.md); design details are in [design-track-proposal.md](design-track-proposal.md).

- **Design session** (`design_sessions` table): a piece of design work done with the `pivot-design` skill, with a title, a target project (folder name or repo), a surface ("pricing page") and a status `exploring` → `approved` → `building` → `done` (or `abandoned`). A session opens only with the **first complete brief**; a small fix does not create a session.
  - **Brief snapshots** (`design_snapshots`, Markdown): only at three milestones, `initial`, `approved` and `major_change` (with a change note). Saving the same brief again at the same milestone returns the earlier snapshot. A `major_change` puts the session back to `exploring`: it must be approved again before work continues.
  - **Decisions** (`design_decisions`): `approval` (sets the session to `approved`; the agent only records one when the user has clearly approved), `change` (the user changes an approved decision), `deviation` (QA finds the result departs from the approved direction).
  - Briefs, decisions, mockups and session notes live only in PIVOT and are **never** written into the target project's repo.
  - **Mockups in a session** (updated 2026-11-03; replaces the earlier decision "mockups are not copied into PIVOT", approved by the owner; details in [mockups-in-pivot-proposal.md](mockups-in-pivot-proposal.md)):
    - **One version is one direction** (added 2026-11-13, see §1 #27): for a multi-page surface, each version contains every page, switched with a CSS page picker inside the mockup itself (`viewer/multi-page.html`); never one version per page.
    - The `design_mockups` table: each `save_design_mockups` call is a **round** (round 1, 2…) of 1–9 versions (`n`, title, self-contained HTML, at most 2 MB each), attached to the latest brief. The HTML is stored directly in the database like the brief's Markdown, not through the blob store. Versions can only be added while the session is Exploring. Older rounds are kept as history. Backup includes this table.
    - Served at `GET /api/design/mockups/[id]` with a strict CSP (`default-src 'none'; style-src 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; sandbox`) and shown in an `<iframe sandbox>`: a mockup cannot run scripts, cannot call other hosts and cannot touch the app.
    - **Inline only inside the mockup's folder** (updated 2026-11-09): when `save_design_mockups` receives a `path`, the inliner (`packages/mcp-tools/src/mockups.ts`) only reads files inside the folder that holds the HTML file, checking both the path as written and the real path after following symlinks, comparing by path segments and not by string prefix.
      - **The input HTML file** (updated 2026-11-09, after the PR #70 security review) is also untrusted input: it must be an absolute path to a regular file ending in `.html` or `.htm`, not a symlink, with no other hard link (`nlink` = 1) and no larger than 2 MB. These conditions are checked on the opened descriptor, before reading the contents. The `.html` suffix is only a filter and does not prove the file is safe: any text file stored under that name is still read as a mockup.
      - Each reference is percent-decoded exactly once and resolved relative to the document or stylesheet that contains it.
      - Only regular files with exactly one name are read (a file with another hard link is rejected, because a hard link can point to a file outside; assets hard-linked from the pnpm store are therefore also rejected): `.css` for `<link>` and `@import`; images and fonts (png, jpg, gif, webp, avif, svg, ico, woff, woff2, ttf, otf) for `url()` and image attributes.
      - The inlined total is at most 2 MB, counting nested CSS and each reuse of a file. Size is checked before reading. `@import` goes at most 4 levels deep, and loops are stopped.
      - **Fail closed**: if a reference might escape the folder or exceed the budget, the whole call is rejected (`invalid_input`) and no version is saved. Rejected cases: POSIX or Windows absolute paths, an escaping `..`, encoded traversal, NUL, the `\` character, `file:` URLs, broken percent-encoding, symlinks pointing outside, directories, FIFOs, sockets, devices. The error names only the reference as written, never the file's contents.
      - Remote URLs, protocol-relative URLs and other schemes are not fetched; they are dropped and listed. A file inside the folder of the wrong type, or a looping or too-deep `@import`, is skipped and listed (`skipped`).
      - Scripts (including unclosed tags), `<iframe>`, `<object>`, `<embed>`, `<base>` and `<meta http-equiv>` refresh, CSP or set-cookie are all removed, in a single linear pass over the HTML size.
      - **Known gap (F1, not yet handled; needs the owner to decide whether to accept the risk)**: a process writing into the mockup folder at the same time can swap a parent directory for a symlink and swap it back, exactly between the check and the file open, and then a file outside can be read. The re-checks after opening only narrow this window and do not close it: 940/4000 leaks were measured with a process swapping continuously.
        - Condition: another process must run at the same time and be able to write into the mockup folder. This folder is created by the agent itself (Claude Code) in scratch.
        - Severity varies with the configuration:
          - When the agent is not sandboxed, it can already read every file of the user, so the race grants no extra permission (low).
          - When the agent runs in a sandbox and the MCP server does not, a prompt-injected agent could use this race to ask the MCP server to read a file the sandbox forbids (medium). In that configuration, passing a `path` straight to any `.html` file has the same property.
        - No root directory is configured to restrict paths: the mockup lives in scratch, outside Claude Code's workspace roots, so restricting to a workspace root would break the workflow.
        - A spike (outside the product) showed that only a read that pins the directory (cwd or a fixed fd, `O_RESOLVE_BENEATH | O_NOFOLLOW_ANY` or `openat`) closes the race. By direction, no native helper or separate OS-specific reader process is brought into the product.
      - A valid mockup produces byte-identical HTML to before, so the digest does not change. Saved mockups and approvals are not modified.
    - **Open the preview from PIVOT** (added 2026-11-17): the session page has an **Open interactive preview** button for the round being viewed (`POST /api/design/sessions/:id/preview` with `round`; needs the same origin or an API token like every write). The PIVOT server itself runs the `pivot-design` skill's `preview.mjs` from this checkout (the path can be changed with `PIVOT_PREVIEW_SCRIPT`), with `--url` set to PIVOT itself; each session has only one window, and opening another round closes the old window. `GET` returns the status (open, round, the latest open error) and the **pending choice**: when the user clicks **Choose this version** in the opened PIVOT window, the server reads the `chosen` line and holds the choice (in memory only, dropped if it no longer matches the stored version and digest); the page switches to that version and opens the **Approve this version** dialog once, pre-filled with the note written in the preview. The choice is not an approval: the owner passphrase is still required. `DELETE` drops the choice; the page also drops it once the approval is done.
    - **Interactive preview** (added 2026-11-10): `node <skill pivot-design>/scripts/preview.mjs <sessionId> [--round n] [--url …]` opens a separate Chromium window for one mockup round.
      - **Controls:** a tab per version (keys 1–9, ←/→), Desktop/Tablet/Phone, Motion: full/reduced (emulates the browser's `prefers-reduced-motion`), Replay and Compare. Each tab shows the version's id and digest, the same digest PIVOT shows next to **Approve this version**.
      - **Integrity:** every version is fetched from PIVOT and its digest is recomputed before it is shown. If even one version does not match, nothing is shown at all (exit 2).
      - **Isolation:** a local server on `127.0.0.1` serves only the checked versions, from memory, reading no files. The browser reaches out only through the motion QA gate, which allows only the preview's own origin and never PIVOT; WebRTC and DNS are turned off, and the WebRTC constructors are removed. Each version runs in a sandboxed frame with an opaque origin and a strict CSP, and cannot touch the control page. The privileged controls (reduced motion and version choice) answer only the preview's page, not the mockup's frame.
        - Each version is served only with its own unguessable token. Only the preview page knows the token, so one version cannot open another under its own label.
        - The server answers only the exact `Host` `127.0.0.1:<port>`, so DNS rebinding reads nothing.
        - `--url` must be PIVOT on this machine, and the answer must be for the session that was asked about.
        - After a crash, the preview reopens at a notice and waits for the user to choose a version; after 3 crashes within a minute the preview stops.

## 16. Image annotations, interaction states, asset extraction (added 2026-11-01)

Per Part B of [PIVOT_DECISIONS.md](PIVOT_DECISIONS.md), decisions #29, #32, #33.

- **Image annotations** (table `asset_annotations`; `GET|POST /api/resources/[id]/annotations`, `PATCH|DELETE /api/annotations/[id]`): a pin or a region with a note on one image of that same reference. The position is stored as a fraction of the image (0–1), so it is correct at every size; a region cannot extend past the image edge. This is a **separate layer**: the image pixels do not change (unlike private-image masking, which edits pixels before upload). The detail page has a **Notes** button next to the image label: drag to create a region, click to drop a pin, write the note in the list; keyboard use: "Add a box", arrow keys move, Shift + arrow keys resize, Delete removes. A partial edit (only the note, only the position) leaves the rest unchanged. MCP `get_reference` returns the annotations (content, kind, position, which image) along with the clean image, and the section context too.
- **Interaction states** (#33): when the page is already saved, the popup has "Add this view as a state of …": pick the state currently showing (Default, Hover, Focus, Open menu, Expanded, Selected, Error, Empty, Loading, Success, or a custom name) and the tab screenshot is added to **that reference** with role `state` and `meta.state`, without creating a new reference (`/api/clip` accepts `attachTo` and `state`). The extension does not click anything on the page itself: the user puts the page into that state first. For a private page, the state also waits for approval like any other save.
- **Selective asset extraction** (#32): the "Pick assets" popup lists the images currently showing (by URL), inline SVG icons, fonts in use (name, weight, style, where served from if readable) and CSS gradients. The user picks, up to 20 files at a time; no bulk download, no copying of pages. `POST /api/resources/[id]/extract`: images are fetched by the server through the SSRF guard (public addresses only), each file keeps its original URL; SVGs are stored as files; fonts **store only the name** (`meta.fonts`, `meta.fontSources`), the font file is not downloaded; gradients are stored as CSS text (`meta.gradients`). Assets attach to the page's reference, so the page must be saved first. An item that fails is reported on its own, and the other items are still saved.

## 17. Backup, restore, sharing, moving machines (added 2026-11-01)

Per Part B of [PIVOT_DECISIONS.md](PIVOT_DECISIONS.md), decisions #38, #39, #40, #41, #51.

- **Backup** (Settings › Backup & restore, `POST /api/backup`): a `pivot-backup-<timestamp>` folder inside the export folder, containing `manifest.json` (format, version, counts), `data.json` (every live reference with its original id, tags and facets, collections, links, image annotations, design sessions, pending suggestions, capture settings) and `assets/<sha256>.<ext>`. It contains no API token, cookie or password; items in the Trash are skipped. The AI-context export (§8) stays separate; MCP remains the default route for Claude Code.
- **Restore** (`POST /api/backup/preview`, `POST /api/backup/restore`; updated 2026-11-10: restore needs the owner passphrase and rejects requests that carry an API token, because a backup contains approval words and design session state): always a **preview** first (how many items are new, how many already exist by the same id or the same URL), and only then a write. New items are imported with their original id. Existing items follow the chosen option: **Keep** (default, changes nothing), **Merge** (only fills empty fields and adds missing facets, collections, files and notes; images from the backup come in as attachments, so the existing Latest and Original stay as they are; existing data is never overwritten), or **Import as new** (a separate copy, writes `meta.importedFrom`). Running it again creates nothing more. Files are reused by sha256. It rejects a folder that is not a backup, a backup from a newer version, a `data.json` over 200MB, file names that are not of the form `<sha256>.<ext>` (blocks path traversal), symlinks, and files whose sha256 does not match.
- **Share package** (selection bar › **Share package**, `POST /api/share`; shown only while Other resource types is on, §1 #34): a read-only folder containing `index.html` (a static gallery), the Latest images and states, and `share.json` (titles, links, descriptions, facets). By default it **leaves out** notes, image annotations and items saved from private pages (`meta.privatePage`, set by the extension when a page is flagged private). There is no public, expiring or revocable share link yet, because the API only answers this machine; a folder that has been sent out cannot be revoked.
- **Moving machines** (#51): the extension options page has a **Waiting saves** section: "Export waiting saves" downloads a JSON file containing the waiting items (with images, keeping the private-approval waiting state) and the server address, with **no** token. "Import a file" shows the item count first and skips items that already exist, so importing twice does not create duplicates. The extension cannot block an uninstall: export first. Items that are already synced live on the server, so they need no transfer.
- **Data retention** (#38): saved data is never cleaned up automatically. The Trash still empties itself after 30 days as before; images between the Original and the Latest are deleted when the page is captured again (§12); the Original, design versions, notes and items waiting to sync are never deleted automatically.

## 18. Searching external sources and Capture Session (added 2026-11-01)

Per Part B of [PIVOT_DECISIONS.md](PIVOT_DECISIONS.md), decisions #6, #7, #36 (Optional group).

- **Hybrid Search (Free-First)** (added 2026-11-01, #6, #7; plan [hybrid-search-plan.md](hybrid-search-plan.md), decisions [PIVOT_DECISIONS.md](PIVOT_DECISIONS.md) §8):
  - **Three scopes:** when there is a keyword in the library, the tool row has an **All / Library / External** switch (parameter `?scope=`, default `all`, not written to the URL). `Library`: library only; if there are no results there is a "Search outside your library" button. `External`: only the outside part (library counts hidden). `All`: library first, then the outside part. The section's folder shelf is hidden while searching. ⌘K has the same switch; in `All`/`External` it shows up to 3 direct results per source (group "<name> · Direct · <license>", choosing one opens that item's page) and a group of search links on the saved Sources' sites.
  - **Direct Search** uses only public, free catalogs that need no key: **Magic UI** (`registry.json`, MIT, the `registry:ui` components whose names are in the official free list `https://magicui.design/llms.txt`; items not on the list are dropped, and if the list cannot be read that sync fails safe: the previously confirmed copy is kept, and if there is none the source reports `unavailable`; on 2026-11-02: 78/78 were on the list), **React Bits** (`registry.json`, MIT + Commons Clause, merging the 4 variants JS/TS × CSS/Tailwind into one component; only name, description and link) and **shadcn/ui** (`index.json`, MIT). Each result has a name, a description (plain text, at most 280 characters), a link to that item's page, a "Direct" label, the license, an attribution line `<name> (<host>) · <license>` and the catalog date. The page link is confirmed by the official sitemap (Magic UI, React Bits) or by the docs link in the catalog (shadcn); an item that cannot be confirmed links to the source's catalog page and says "opens the … catalog" (no Save button).
  - **Catalogs** are downloaded on the first search, then at most once every 24 hours, or when Refresh is clicked in Settings › Search (at most once a minute; clicking again within a minute reports that the catalog was just updated and was not reloaded); they are **stored on Cloudflare R2** (updated 2026-11-02, Cloud-First: replaces the earlier local-only storage requirement) under the key `external-catalogs/v1/<source>.json`, separate from the reference files; a catalog file is never written to disk. R2 is chosen explicitly: if the `R2_*` keys are missing, Direct Search reports `unavailable` ("R2 isn't configured") and does not silently switch to disk. While searching, the catalog is held in memory (at most one catalog per source, at most 5000 items per catalog); R2 is read only when memory does not have it yet (once per catalog after startup), and written only after a successful sync from the source (at most daily or on Refresh); searching does not call R2. If R2 cannot be read, the in-memory catalog is used if there is one, otherwise that source reports `unavailable`; if R2 cannot be written, the freshly downloaded catalog is still usable in memory (with a note). R2 operations may incur small charges. A catalog contains only id, name, description, link and category; it **never contains code** (a catalog that contains code is rejected). Searching runs on this machine using the library's own query parser (`parseQuery`), makes no network call per search and writes nothing to the database. If a download fails, the latest good copy is used (status `stale`, with a note); if there is none, that source reports `unavailable`; each source fails on its own and does not break the whole page. Settings › Search turns each source on or off (`app_settings` key `search`), and shows the item count, catalog date, license, and Refresh.
  - **Link-out:** every other source (including paid ones such as Mobbin, Refero, Nicely Done, Savee, and SiteInspire pending license verification) is only a link that opens that site's own search page, in the "Search on other sites" section: "These open each site’s own search page. They aren’t results." It is never shown as a result.
  - **Save:** only when you click "Save to library" on a result: it saves through `/api/clip` (skipped if the same URL and type already exist), type Reference, into the Inbox, and the server captures the page; `meta.externalOrigin` records the source, id, license, catalog time and save time, and the detail page shows "Found via <source> (<license>) search". The catalog's description is kept only when the license covers the whole catalog (MIT); for React Bits the server reads the description from the page. A result that is already in the library (same URL) shows "In your library" instead of Save.
  - **API:** `GET /api/search/external?q=&providers=&category=&limit=` (`q` 1–120 characters; there is no field for context such as a brief or notes) returns `{ query, providers: [{ id, name, status, message?, syncedAt, total, results }], linkOuts }`; `GET|PATCH /api/search/providers` (on/off), `POST /api/search/providers/refresh`. `/api/capabilities` has `search.external`.

  - The extension keeps **Elsewhere** as links that only open (§4).

## 19. Gate 1: references proposed for a design session (added 2026-11-10)

- **Session opened from the start:** `pivot-design` opens a design session right after it understands the request, with `save_design_brief` (`initial`) and a short `## Requirements` brief; the full brief is saved later into the same session.
- **Proposing** (`propose_references`, `POST /api/design/sessions/[id]/candidates`): the agent puts 6–10 references into the session, numbered 1, 2… per session. A reference in the library is sent by `resourceId`. An outside page is sent by `url`: only public http/https (through `assertPublicUrl`, which blocks internal addresses), with the source where it was found (web search, gallery, catalog). Each reference has a `category` of `layout` or `component` (added 2026-11-15, §1 #29), which the agent writes or PIVOT infers. Each item has `why` (required), `take`, `avoid`. At most 12 items per call, 30 items per session; the same reference or the same URL cannot be proposed twice. Only while the session is Exploring.
- **PIVOT captures the preview itself:** for each outside page, PIVOT captures a 1440×900 viewport using the capture Chromium (the same network guard layer; pages that block bots or return HTTP errors are rejected as in §12), runs three pages at a time in the background, stores a WebP through the blob store (`design-candidates/<session>/<id>.webp`) and serves it at `GET /api/design/candidates/[id]/preview`. A page that cannot be captured is still listed, with the reason. The MCP tool waits up to 120 seconds for the previews and then returns them to the agent as images, so the agent can check what it wrote. A library reference uses its existing cover image.
- **Not saved to the library:** an outside page belongs to the session only (table `design_candidates`, migration 0011, adds a table only). It is saved to the library only when the user asks (`save_reference`). Backup does not include this table yet.
- **The user chooses** (`select_references`, `POST /api/design/sessions/[id]/candidates/select`): the agent records exactly the numbers the user gave, with the user's words verbatim (required); a new choice replaces the old one. After giving the list, the skill stops its turn and never chooses by itself, unless the user says "you choose" (in which case it quotes those exact words).
- **The session page** shows a **References** section (updated 2026-11-17: after the mockups, or right under the page head when there are no mockups yet), split into two groups, **UI layouts** then **Components** (added 2026-11-15, see §1 #29; an empty group is hidden), each group a grid of numbered cards with the preview (or "Capturing a preview…", or the reason there is none), title, Library or External · source, a link to the original page (new tab) or to the page in the library, and Why/Take/Avoid; after a choice (updated 2026-11-17), the section shrinks to one row of the picked references (small preview, number, title, link) and "3 picked of 10"; **Show all 10 references** reopens the whole grid, where the chosen items carry a **Picked** label, the preview images of the other items are dimmed (text keeps its contrast), and the user's words are quoted. `get_design_session` lists the items and the choice.
